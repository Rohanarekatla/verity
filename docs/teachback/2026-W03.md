## A → B: pixel sampling and glyph-region estimation

*Notes written by B (Nikhil)*

**What Rohan built (A3.1–A3.5):**

`node-worker/static/sampling.ts` adds a `sampleRegion` RPC method. Given an
artifact and a selector, it reads the **actual rendered pixels** for that
element off the still-open Chromium page and returns:

- `foreground` — the text colour, as RGB
- `background_samples` — a *list* of background colours with pixel counts
- `text_pixel_count` / `background_pixel_count`
- `sampled` — whether it worked at all
- `ambiguous` — whether the text/background split can be trusted

The two design choices that matter to my side:

**A per-region sample set, not one averaged colour (A3.3).** This is what
makes worst-case contrast possible. White text on a sky that darkens toward
the horizon is readable at the top and invisible at the bottom; the average
background is a colour that appears nowhere on screen and produces a ratio no
reader ever experiences. Because Rohan returns the set, I can take the
minimum.

**The `ambiguous` flag (A3.2).** Glyph-region estimation separates text pixels
from background pixels. When background coloured near the text gets swallowed
into the text class, the "foreground" colour is no longer purely the text
colour — so any ratio computed from it measures something that is not there.
Rohan flags it rather than returning a confident wrong answer, and my
adjudicator turns that straight into `cantTell`. This is the single most
useful thing in the payload for the zero-false-positive gate.

He also changed the page lifecycle: `runAxe` no longer closes the page,
because `sampleRegion` needs the same pixels afterwards. The orchestrator now
owns releasing it via `releaseArtifact`.

A3.5 registered my `contrast_over_image` injector in the corpus, which was
the gate blocker.

**Thin spots — things I could not explain unaided:**

- How glyph-region estimation actually decides which pixels are text. I know
  *that* `ambiguous` is set, not the rule that sets it.
- Why the top background sample is exact (`#808080` came back as exactly
  128,128,128) rather than approximately — antialiasing should smear it.
- What happens on a page where the element moves between `render` and
  `sampleRegion`.

## B → A: worst-case ratio and the adjudication band

*Notes on Nikhil's Track-B contrast adjudication, written by Rohan.*

The thing that clicked for me about Nikhil's side is that it does almost
nothing clever — and that's the point. My `sampleRegion` hands it a pile of
measured colours; his code does WCAG arithmetic over them and refuses to guess
anywhere the arithmetic is ambiguous. No model is in this path at all.

**Worst-case, not average — and why my sample set is the whole reason it
works.** `worst_case_ratio()` takes the *minimum* contrast ratio between the
foreground and any background colour in the set, not the mean. White text over
a sky that darkens toward the horizon is fine at the top and invisible at the
bottom; an average background is a colour that appears nowhere on the element
and yields a ratio no reader ever sees. This is why A3.3 returns a *set with
counts* rather than one averaged colour — if I'd averaged on my side, his
worst-case would be unrecoverable. The two decisions are one decision made on
two sides of the RPC.

**How an `incomplete` becomes `authoritative` with no model.** axe marks text
on an image `incomplete` because it can't read the background from CSS. It's
not that the contrast is unknowable — it's that *axe* can't see it. The browser
can: my sampler reads the real rendered pixels, and once you have the actual
colours, the WCAG formula is deterministic. So the verdict is every bit as
authoritative as a plain axe contrast finding; the only thing that was missing
was the measurement, and we took it rather than asked a model to estimate it.
That's ADR-0003 in practice.

**The 3.0–4.5 band and why it's `cantTell`, not a verdict.** WCAG wants 4.5:1
for normal text but only 3:1 for large text, and `RegionSample` carries no font
size. So the adjudicator can only decide where *both* thresholds agree: ≥4.5
passes regardless of size, <3.0 fails regardless of size, and the band between
is genuinely undecidable from what we measured — it depends on a font size we
don't have. Assuming 4.5 there would fail compliant large text, which is the
exact false positive the Week 3 gate forbade. The band is a gap in the input,
not the maths — and closing it is on me (add fontSize/fontWeight to the
sample), which I've now signed up to in ADR-0003.

**Why `ambiguous: true` can never pass.** When my glyph/background split is
untrustworthy — "text" pixels outnumber background pixels, so a
near-foreground background patch got swallowed into the text class — the
worst-case background I report may be missing the actual worst pixel. Nikhil's
code maps `ambiguous` straight to `cantTell` / needs-review and never lets it
pass, because a pass computed from an incomplete worst-case is exactly how a
real failure hides. It's the single most load-bearing flag in the payload for
the zero-false-positive gate.

**What `worst_case_ratio()` returns on an empty set, and why not 0.** It
returns `None`, not `0.0`. Zero would be the *worst possible* ratio and would
manufacture an authoritative failure out of "we have no samples" — a
fabrication. `None` means "undecidable", the caller turns it into
`cantTell`/needs-review, and nothing gates. "We learned nothing" and "it
failed" must never be the same value; that's the same lesson as `cantTell`
carrying confidence 0.0 from W02.
