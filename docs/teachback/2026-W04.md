## B → A: three-state outcomes, and why a pass is harder than a fail

*Notes on Nikhil's Track-B keyboard judgments, written by Rohan.*

Building the traversal taught me why Nikhil's side is shaped the way it is: the
whole design is organised around the fact that keyboard checking is *flaky* in
a way pixel sampling isn't, so the honest answer is often "I couldn't tell".

**Three states because two would lie.** `pass` / `fail` / `indeterminate`,
where `indeterminate` maps to `outcome=cantTell`, `provenance=NEEDS_REVIEW`,
`confidence=0.0`, and never gates a build. It is not a soft "fail" — it's the
truthful outcome when the traversal didn't gather enough evidence. Keyboard
focus escapes to browser chrome, widgets hydrate late, transitions fire
mid-flight. Pixel sampling either reads a pixel or doesn't; a Tab traversal can
half-succeed, and the data model has to be able to say so.

**Evidence of a defect stands alone; a pass needs complete coverage.** This is
the subtle one and it's asymmetric on purpose. If I saw a missing focus ring or
a positive `tabindex` on a stop, that's a *fact about the page* whether or not
my traversal finished — so `fail` is assertable from a partial run. But "this
page passes keyboard" is a claim about *every* stop, including the ones I never
reached, so it requires `complete=True`. Nikhil's first `judge_focus_visible`
got this backwards — reported 2.4.7 satisfied on a traversal that died halfway
— and a test caught it. This is also why my side has to report `complete`
honestly: if I claim a truncated run finished, his code turns my truncated stop
list into fabricated passes. The two sides meet exactly on that boolean.

**`focus_visible` None vs False must not collapse.** `None` = "A4.3 didn't
measure this stop"; `False` = "measured, and there's no indicator". If my
worker sent `False` for stops I simply didn't measure, his judge would report a
2.4.7 failure on every one of them — a fabricated failure, and the gate says
zero false alarms. So on my side an unmeasured stop is `None`, always, and I'd
rather send `None` than a guess. His code treats the two as different inputs,
which only works because I keep them different.

**`ARROW_NAVIGABLE`, and the tablist that shows five "unreachable" tabs.** A
correct APG tablist with six tabs exposes one Tab stop; the other five carry
`tabindex="-1"` and move under the arrow keys — the roving-tabindex pattern.
Tab never lands on them, so a naive traversal reports five unreachable controls
and his 2.1.1 judge screams on a textbook-correct widget. The fix is on my
side: I classify those as `ARROW_NAVIGABLE` (reachable, by a different key),
and he deliberately keeps that category out of both the barrier list and the
blind-spot list — it's not a problem at all. This category didn't exist until
the tablist contract named it, which is the argument for rule 3 of ADR-0004.

**Why running out of retries never becomes `fail`.** The retry policy re-runs
while anything is indeterminate, capped at 3 attempts. When the cap is hit with
things still indeterminate, the result stays `indeterminate` — it does not
escalate to `fail` or settle to `pass`. "We tried three times and still
couldn't tell" is still "couldn't tell"; converting exhausted attempts into a
verdict would be inventing a result the evidence doesn't support, which is the
same sin as collapsing `None` into `False`.

## The thing worth discussing at the session

The `ARROW_NAVIGABLE` reason code did not exist until the tablist APG contract
was written. Writing the contract *before* the runner code — which the plan
required and which we nearly skipped — is what surfaced it. Without it the
checker would have reported five unreachable tabs on the first APG reference
implementation we pointed it at, and failed the gate on a widget built exactly
to spec.

Worth deciding jointly: is "write the contract first" a rule we keep for every
widget pattern in Weeks 5+, or was this a one-off?
