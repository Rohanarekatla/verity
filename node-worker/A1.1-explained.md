# A1.1 — The JSON-RPC Worker, Explained

**Verity · Week 1 · Engineer A**

This document explains the code in `node-worker/`: what it does, why each decision was made, the failure modes it guards against, and how to talk about it in an interview.

Read it with the code open. Every section maps to a file.

---

## Part 1 — What are we actually building?

### 1.1 The problem this solves

Verity has two halves that must talk to each other:

- **Python** owns orchestration, ML models, and the trust machinery. Python has the ML ecosystem.
- **Node** owns the browser. Playwright and axe-core are JavaScript libraries. There is no good Python equivalent — `axe-core` in particular is *the* accessibility rules engine, and it runs inside a browser page.

Neither language can do the other's job well. So the architecture is a **polyglot system**: a Python orchestrator that spawns a long-lived Node subprocess and sends it commands.

A1.1 builds the pipe between them. Nothing more.

### 1.2 Why a subprocess and not an HTTP server?

This is the first question an interviewer will ask, so be clear on it.

| Option | Why not |
|---|---|
| HTTP microservice | Needs a port, service discovery, health checks, and a deployment story. Verity is a CLI tool a developer runs locally and in CI — asking them to run two services is a non-starter. |
| Rewrite axe-core in Python | Thousands of hours, and you'd be reimplementing the reference implementation the entire industry trusts. Instant credibility loss. |
| Call Node per-request (`subprocess.run` each time) | Node startup is ~50ms and browser launch is ~500ms. On a 25-page crawl with multiple calls per page you'd pay that hundreds of times. |
| **Long-lived subprocess over stdio** ✅ | One process, one browser launch, no ports, no network, no auth. The OS gives you the transport for free. |

The key insight: **the browser is expensive to start and cheap to reuse.** A long-lived process lets you launch Chromium once and drive it for the whole audit. That is the entire reason for this design.

### 1.3 Why JSON-RPC 2.0 specifically?

We need a request/response protocol over a byte stream. We could invent one. We don't, because:

- It's a tiny, stable, well-documented spec — you can read the whole thing in fifteen minutes.
- It has defined semantics for errors, which is the part people always get wrong when rolling their own.
- **It's what the Language Server Protocol and the Model Context Protocol use** — both are editor/agent talking to a subprocess over stdio, exactly our shape. Choosing it means you're following a proven pattern rather than an invented one, and that's a strong signal in a design conversation.

We implement a deliberate subset: no batching, no server-initiated requests. Those add complexity we don't need.

### 2.1 `protocol.ts` — the contract

This file is the **interface definition** between Python and Node. If you change it, the other side breaks. Treat it accordingly.

A request looks like:

```json
{"jsonrpc": "2.0", "id": 1, "method": "ping", "params": {}}
```

A success response:

```json
{"jsonrpc": "2.0", "id": 1, "result": {"pong": true}}
```

A failure response:

```json
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "unknown method"}}
```

**The `id` is the important field.** Every response carries back the id of the request that caused it. This is what lets the client match responses to requests when they arrive out of order — which they will, because we don't block.

#### Error codes

The spec reserves `-32768` to `-32000`. We use the standard ones and define our own outside that block:

| Code | Name | Means |
|---|---|---|
| -32700 | PARSE_ERROR | The line wasn't valid JSON |
| -32600 | INVALID_REQUEST | Valid JSON, but not a valid request object |
| -32601 | METHOD_NOT_FOUND | No such method |
| -32602 | INVALID_PARAMS | Method exists, params are wrong |
| -32603 | INTERNAL_ERROR | Handler threw unexpectedly |
| **-31001** | **NOT_IMPLEMENTED** | Method is declared but not built yet |
| -31002 | HANDLER_TIMEOUT | Handler exceeded its budget |

**Why `NOT_IMPLEMENTED` is separate from `METHOD_NOT_FOUND`:** if `render` simply didn't exist, Engineer B gets `-32601` and can't tell whether they typo'd the method name or whether you haven't built it yet. Two very different debugging paths. A distinct code makes it unambiguous. This is a small decision that shows you're thinking about the person consuming your API.

### 2.2 `framing.ts` — the concept people get wrong

**This is the most important idea in A1.1 and the one most likely to come up in an interview.**

stdin is a *byte stream*, not a *message stream*. When you write this:

```javascript
process.stdin.on('data', (chunk) => {
  const request = JSON.parse(chunk.toString());  // ❌ WRONG
});
```

…it works perfectly on your machine, for weeks, and then breaks in production.

The reason: **one `data` event does not equal one message.** A chunk may contain:

- half a request (the rest arrives in the next chunk)
- exactly one request
- three requests and a fragment of a fourth

The OS pipe buffer is typically 64KB. Small `ping` requests always fit, so naive parsing looks correct. But `render` will eventually return the full DOM of a page — hundreds of kilobytes — and then the stream fragments and everything breaks at once.

**The fix is framing:** agree on a delimiter that marks a message boundary. We use newline. This works because `JSON.stringify` escapes real newlines inside strings as `\n` (two characters, backslash and n), so a raw `0x0A` byte can only ever be our delimiter.

The decoder buffers whatever it receives, splits on newlines, emits complete lines, and keeps the trailing partial line for next time:

```typescript
push(chunk: string): string[] {
  this.buffer += chunk;
  const lines: string[] = [];
  let newlineIndex: number;
  while ((newlineIndex = this.buffer.indexOf("\n")) !== -1) {
    const line = this.buffer.slice(0, newlineIndex);
    this.buffer = this.buffer.slice(newlineIndex + 1);
    if (line.trim()) lines.push(line.replace(/\r$/, "").trim());
  }
  return lines;
}
```

There's also a max-line guard. If we accumulate 64MB without seeing a newline, the peer isn't speaking our protocol and we fail loudly rather than growing memory until the process dies.

> **The alternative:** LSP uses `Content-Length: N\r\n\r\n<N bytes>` headers instead of newline delimiting. That's more robust (no delimiter can appear in the payload at all) but more code. Newline-delimited JSON is the right call when you control both ends. Know both — an interviewer may ask why you didn't use length-prefixed framing.

### 2.3 `log.ts` — protecting the channel

**Rule: stdout carries protocol frames and nothing else.**

A single stray `console.log("debugging...")` writes a non-JSON line to stdout, the client tries to parse it, and the stream desynchronises. The failure looks like a mysterious parse error unrelated to the code you were actually debugging.

Discipline doesn't scale here, so we make the mistake structurally impossible:

```typescript
export function guardStdout(): void {
  console.log = redirect("info");
  console.error = redirect("error");
  // ...
}
```

Any `console.log` — yours or a dependency's — gets redirected to stderr with a warning. This matters more than it sounds: Playwright and several transitive dependencies print to stdout under certain failure conditions. Without the guard, a browser warning corrupts your protocol.

Logs go to stderr as structured JSON lines, which means you can `grep` them, and the Python side reads stderr on a separate pipe and ignores it entirely.

### 2.4 `dispatcher.ts` — never leave the caller hanging

The dispatcher does three things. The third is the one that matters.

**1. Method registry** — name → handler mapping.

**2. Per-call timeouts** — `ping` gets 5s, `render` gets 120s (browsers are slow), `runAxe` gets 60s. Without this, one hung page wedges the entire worker and the audit never completes.

**3. Total error containment** — `invoke()` never throws. It always resolves to either a result or a structured error body.

That third point deserves emphasis:

> **A hang is worse than a failure.** If a handler throws and we send nothing back, the Python client is left awaiting a future that will never settle. The symptom appears minutes later as an unexplained freeze, with no stack trace and no indication of which call caused it. If instead we return `{"error": {"code": -32603, "message": "..."}}`, the failure surfaces in one second with a cause attached.
>
> **This is the single most valuable design principle in the file, and it generalises far beyond this project.** Any time you own one side of an async boundary, your obligation is to *always answer* — even when the answer is "I failed."

### 2.5 `server.ts` — the wiring

Reads stdin → decodes frames → validates → dispatches → writes responses.

Three details worth understanding:

**Requests are not awaited in order.** We call `void handleLine(line)` in a loop without awaiting. A slow `render` doesn't block a fast `ping` queued behind it. This means responses can come back out of order — which is legal JSON-RPC and precisely why every response carries an `id`.

**Malformed input still gets a reply.** If `JSON.parse` fails we respond with `id: null` (we couldn't read an id). If validation fails but we *could* extract an id, we use it — so the client can settle the right promise instead of timing out.

**Framing errors are fatal.** If we lose track of where messages begin, we can't recover. We log, send a final error, and exit. Better a clean crash than silent corruption.

## Part 3 — The bug the tests found

This is the most interesting part of the exercise, and worth telling as a story.

The first test run gave 14/15 passing. The failure:

```
not ok 11 - a large payload spanning the pipe buffer survives framing
error: 'stdout contained a non-JSON line: {"jsonrpc":"2.0","id":7,"error":{"code":-31001,...,"data":{'
```

The response was **truncated mid-object**.

**The cause:** when stdout is a pipe (which it always is here — Python spawns us with `stdio=PIPE`), writes larger than the pipe buffer are *asynchronous*. `process.stdout.write()` returns immediately and Node flushes in the background. But `process.exit()` does **not** wait for pending writes. It terminates immediately and the partial write is lost.

**Why it stayed hidden:** the acceptance criterion is

```bash
echo '{"jsonrpc":"2.0","id":1,"method":"ping"}' | node dist/rpc/server.js
```

The `ping` response is ~150 bytes. It fits in the buffer, flushes synchronously, and looks perfect. The bug only appears with large payloads — which is exactly what `render` will produce in two days' time.

**The fix** — count pending writes and drain before exiting:

```typescript
let pendingWrites = 0;

function respond(response: unknown): void {
  pendingWrites += 1;
  process.stdout.write(encodeFrame(response), () => { pendingWrites -= 1; });
}

// in shutdown(), after waiting for in-flight handlers:
while (pendingWrites > 0 && Date.now() < deadline) {
  await new Promise((r) => setTimeout(r, 5));
}
```

**Why this matters beyond the fix:** the acceptance criterion in the plan is a *floor*, not a definition of done. A test suite that only checks the happy path would have shipped this, and you'd have spent Thursday debugging "sometimes render returns invalid JSON" while assuming the problem was in the renderer. It was in the transport, written two days earlier.

That's the lesson: **test the boundary conditions of infrastructure code immediately, because infrastructure bugs surface as bugs in whatever is built on top of it.**

## Part 4 — Difficulties you will hit

Ordered by how likely they are to bite you.

### 4.1 The stdout corruption trap

**Symptom:** intermittent parse errors on the Python side. Works fine sometimes.
**Cause:** something printed to stdout — a `console.log`, a dependency warning, a deprecation notice.
**Prevention:** `guardStdout()` runs before anything else. Already handled, but *understand why it's there* — you'll be tempted to remove it when debugging.

### 4.2 Buffering deadlock

**Symptom:** both processes hang, no CPU usage.
**Cause:** Node fills the stdout pipe buffer and blocks waiting for Python to drain. Python is blocked writing to stdin waiting for Node to read. Classic deadlock.
**Prevention:** on the Python side, always `await drain()` after writing, and read stdout and stderr on separate concurrent tasks. **Never let stderr fill up** — if nobody reads it, the buffer fills and Node blocks on its next log write, which looks exactly like a hang in unrelated code.

### 4.3 Truncated writes on exit

Covered in Part 3. Fixed here — but the same trap exists on the Python side. Don't `kill()` the subprocess when you can close stdin and let it exit cleanly.

### 4.4 Zombie processes

**Symptom:** dozens of orphaned `node` processes after a crashed test run; laptop fans spin up.
**Cause:** Python died without terminating the child. The child keeps its browser open.
**Prevention:** Python should use `try/finally` around the subprocess lifecycle. On the Node side, handle `SIGTERM` and `SIGINT` (done) and consider exiting when stdin closes (done — the `end` event triggers shutdown).

### 4.5 The `id` type trap

JSON-RPC allows string or number ids. If you `parseInt` an id or coerce it to a string, `"1"` and `1` become the same key and responses go to the wrong promise. There's a test for this specifically. Preserve the type exactly.

### 4.6 Windows line endings

If your friend develops on Windows, a request may arrive terminated with `\r\n`. Strip the `\r` or `JSON.parse` fails on the trailing character. Handled in the decoder, tested.

### 4.7 What will bite you in A1.2 (not yet)

Two days out, but worth knowing now:

- **Playwright must be launched once, not per call.** Put the browser instance in module scope, launch lazily on first `render`, close on shutdown.
- **`page.accessibility.snapshot()` has been removed** from Playwright. Use `page.context().newCDPSession(page)` then `Accessibility.getFullAXTree`. Building on the removed API is the most likely way to lose an evening this week.
- **Network idle is not enough** for SPAs. You need network idle *plus* a DOM-mutation settle window, or you'll capture a loading spinner.

## Part 5 — Interview answers

Verity is your portfolio project, so every piece needs a story. Here's how to talk about this one.

### Q: "Walk me through the architecture of your project."

> Verity is an accessibility conformance engine. The core constraint is that the ecosystem's rules engine — axe-core — is JavaScript and runs inside a browser, but the ML and orchestration work is Python. So it's a polyglot system: a Python orchestrator spawns a long-lived Node worker and drives it over stdio using JSON-RPC 2.0.
>
> I chose a subprocess over an HTTP microservice because Verity is a CLI tool that runs locally and in CI. Requiring users to start two services would kill adoption. Over stdio there's no port, no service discovery, no auth — the OS provides the transport.
>
> The process is long-lived rather than per-request because launching Chromium costs about half a second. On a 25-page crawl with several calls per page, per-request spawning would add minutes of pure startup overhead.
>
> JSON-RPC specifically because it's the same shape as the Language Server Protocol and MCP — editor or agent talking to a subprocess over stdio. Rather than inventing a protocol, I used the one that's proven for this pattern.

### Q: "What was the hardest bug you hit?"

**This is your best story. It has a symptom, a non-obvious cause, and a lesson.**

> I had a transport layer passing its acceptance test — send a ping, get a valid response. But I'd written boundary tests, and one of them sent a 300KB payload. The response came back truncated mid-object.
>
> The cause was that when stdout is a pipe, writes larger than the OS pipe buffer are asynchronous. `process.exit()` doesn't flush them — it terminates and the partial write is lost. Small responses fit in the buffer and flush synchronously, which is why the happy path looked perfect.
>
> The fix was to count pending writes with the write callback and drain before exiting.
>
> What I took from it: the acceptance criterion was a floor, not a definition of done. If I'd shipped on the happy path, the bug would have surfaced two days later as "the renderer sometimes returns invalid JSON," and I'd have spent hours debugging the renderer when the bug was in the transport. Infrastructure bugs always surface as bugs in whatever sits on top.

### Q: "How do you handle failures across a process boundary?"

> The rule I settled on is that the dispatcher never throws — it always resolves to either a result or a structured error.
>
> The reason is that a hang is worse than a failure. If the handler throws and I send nothing, the client awaits a future that never settles. The symptom shows up minutes later as an unexplained freeze with no stack trace and no indication of which call caused it. If I return an error object with a code, the failure surfaces in a second with a cause attached.
>
> On top of that: per-method timeouts so one hung page can't wedge the worker, and best-effort id extraction so that even a malformed request gets answered with the caller's id — otherwise the client can't settle the right promise and has to wait for its own timeout.

### Q: "How did you split work with your teammate?"

> Two tracks. I own the browser, deterministic testing, and the CI surface — TypeScript, Playwright, axe-core. He owns orchestration, the ML layer, and the trust machinery — Python, Pydantic, MLX. We rotate a module at every phase boundary so neither of us becomes a single point of knowledge.
>
> The sequencing decision I'd point to: on day one I built the RPC server before anything else, because his client was blocked on the contract existing. I shipped `ping` working and `render`/`runAxe` as stubs that return a distinct `NOT_IMPLEMENTED` code — not "method not found," because that's ambiguous between "you typo'd" and "not built yet." That let him write and test his client, including its error paths, while I was still working on the browser layer.

### Q: "Why didn't you just use HTTP / gRPC / a message queue?"

> All three assume a networked, multi-service deployment. Verity is a single binary a developer runs on their laptop and in a CI container. Adding a broker or a port means adding a deployment story to a tool whose main selling point is that you can `npx` it.
>
> gRPC would give me schema-generated types across the language boundary, which is genuinely attractive — I get that benefit anyway by generating TypeScript types from Pydantic's JSON Schema. But gRPC also brings protobuf tooling, a code generation step in the build, and HTTP/2 for two processes on the same machine that could just share a pipe.

### Q: "How do you know it works?"

> Fifteen tests against the protocol boundary, all spawning a real subprocess rather than mocking the transport. They cover: a request split across chunks, fifty requests arriving in one chunk, a 300KB payload spanning the pipe buffer, malformed JSON, a malformed line followed by valid ones, notifications with no id, CRLF endings, and an assertion that every line on stdout parses as a JSON-RPC frame.
>
> That last one is a guard rather than a test — it catches any future `console.log` that would corrupt the channel.

### Concepts to be able to define cold

If you can't explain these in one sentence, re-read the relevant section:

- **Framing** — the convention that turns a byte stream into discrete messages.
- **Backpressure** — what happens when a writer outpaces a reader; why unread stderr can deadlock a subprocess.
- **Correlation id** — the field that matches an async response to its request when ordering isn't guaranteed.
- **Head-of-line blocking** — a slow request delaying the ones behind it; avoided here by not awaiting in the read loop.
- **Zombie / orphan process** — a child that outlives its parent because nobody reaped it.
- **Polyglot architecture** — using two languages where each has an ecosystem the other lacks, and paying a boundary cost for it.
